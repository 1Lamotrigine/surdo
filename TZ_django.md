# ТЗ и архитектура: ИИ-аватар сурдопереводчик для лекций

Версия 2.1 (Django), по состоянию на 26 ноября 2026 года · Веб-проект для глухих и слабослышащих студентов · Бюджет на людей: ноль, команда 2-3 студента

## 1. Цель и позиционирование

**Цель.** Веб-сервис, в котором преподаватель говорит в микрофон, а аватар в браузере показывает перевод жестами. Студенты видят аватара и субтитры, пишут вопросы в чат, преподаватель видит чат в реальном времени. Ничего устанавливать не нужно.

**Позиционирование.** Ассистент для ситуаций, когда живого сурдопереводчика нет (дистанционка, малые школы и колледжи, регионы). Не замена переводчика. В продукте и питче: «глухие и слабослышащие», «прототип помощника», а не «полноценный перевод на жестовый язык».

**Принципы.**

1. Субтитры всегда рядом с аватаром, это страховка от ошибок.
2. Для учебного пилота жесты проверяет носитель РЖЯ. Стартовый набор Slovo предназначен для демонстрации и импортируется с техническим статусом `verified` без экспертной проверки в проекте.
3. Узкая предметная область на MVP, а не «весь язык».
4. Ставка на словарь клипов, а не на нейросетевую генерацию жестов (она нереалистична при нашем бюджете и данных).

**Статус.** Первая цель — работающий прототип, который можно показывать и потом менять. Язык первой версии: русский (русская речь и РЖЯ). Все ИИ-компоненты берутся готовыми: Whisper, MediaPipe, Kalidokit, готовый VRM-аватар, LLM по API; обучение собственных моделей не планируется. Единственное, что нужно создавать самим, это данные: словарь жестов. Компоненты заменяемы за интерфейсами (распознавание речи, LLM, хранилище клипов, версия формата клипа и словаря), чтобы позже улучшать их по одному.

**Вне рамок MVP:** end-to-end генерация жестов нейросетью, мобильное приложение, видеозвонки, запись лекций, несколько жестовых языков одновременно, перевод связной речи на РЖЯ в русский текст.

## 2. Роли и сценарии

| Роль | Что делает |
| --- | --- |
| Преподаватель | Создаёт комнату, говорит в микрофон (или печатает), видит чат, видит отставание аватара и нераспознанные слова |
| Студент | Заходит по QR-коду или по ID комнаты, смотрит аватара и субтитры, пишет в чат, может регулировать скорость и размер аватара, распознаёт отдельные жесты через камеру |
| Редактор словаря | Записывает жесты, отправляет на проверку, видит статусы |
| Эксперт-носитель | Проверяет жесты: утверждает, отклоняет, оставляет комментарий |
| Админ | Управляет пользователями и комнатами |

**Основной сценарий.** Преподаватель создаёт комнату, на его экране показываются QR-код и ID комнаты. Студент заходит любым удобным способом: сканирует QR-код (телефон сразу открывает сайт внутри этой комнаты) или открывает сайт и вводит ID. Преподаватель говорит. Фразы разбиваются по паузам, превращаются в последовательность глосс, аватар их проигрывает, ниже идут субтитры. Студент пишет вопрос, преподаватель отвечает голосом, цикл повторяется.

## 3. Функциональные требования

### 3.1. Комнаты и чат

- FR-1. Регистрация и вход (email + пароль), роли.
- FR-2. Создание комнаты преподавателем. На его экране крупно показываются QR-код и ID комнаты (удобно вывести на проектор).
- FR-2a. Вход по QR: код содержит ссылку вида `https://<домен>/r/<ID>`. Телефон открывает сайт сразу внутри комнаты, искать сайт не нужно.
- FR-2b. Вход по ID: студент открывает сайт, вводит ID на главной странице и попадает в ту же комнату.
- FR-2c. Студент входит без регистрации, достаточно ввести имя. Регистрация нужна только преподавателю, редактору и эксперту.
- FR-2d. Каждая комната изолирована: фразы, субтитры и чат видят только её участники. Один урок = одна комната.
- FR-2e. ID короткий (6 символов, без похожих O/0 и I/1), действует, пока комната открыта. Перебор ID ограничен rate limit.
- FR-2f. Преподаватель может закрыть комнату, удалить участника и сменить ID (старый QR перестаёт работать).
- FR-3. Чат: сообщения студентов видны преподавателю и всем в комнате, история хранится.
- FR-4. Список участников (presence).

### 3.2. Речь и перевод

- FR-5. Захват микрофона в браузере преподавателя, VAD в браузере делит речь на фразы, готовая фраза уходит на сервер.
- FR-6. Распознавание русской речи через Faster Whisper, каждая фраза распознаётся целиком.
- FR-7. Режим «текстом» вместо микрофона (отладка, шумная обстановка, запасной вариант).
- FR-8. Преобразование фразы в глоссы с грамматическими маркерами (вопрос, отрицание, повеление, число).
- FR-9. Для слов без жеста: дактиль (пальцевая азбука) по буквам, слово попадает в очередь нераспознанных.
- FR-10. Субтитры синхронно с аватаром (подсвечивается текущее слово).

### 3.3. Аватар

- FR-11. 3D-аватар (VRM) в браузере, WebGL, без установки.
- FR-12. Проигрывание клипов подряд с плавным переходом (блендинг 150-250 мс), нейтральная поза между фразами.
- FR-13. Управление студентом: скорость (0.6x-1.2x), размер, положение, тёмный/светлый фон.
- FR-14. Очередь клипов с контролем отставания.

### 3.4. Управление отставанием

- FR-15. Очередь показывает преподавателю индикатор отставания (зелёный до 5 с, жёлтый до 10 с, красный выше) и подсказку «замедлитесь».
- FR-16. При отставании выше порога: ускорение клипов до 1.3x, сжатие фразы через LLM (убрать вводные), пропуск пауз между клипами.

### 3.5. Словарь жестов (инструмент редактора)

- FR-17. Запись жеста с веб-камеры в браузере: извлечение поз MediaPipe (руки, тело, лицо) прямо на клиенте.
- FR-18. Предпросмотр на аватаре, обрезка начала и конца, сохранение клипа.
- FR-19. Статусы жеста: черновик → на проверке → проверен → отклонён. Подбор жестов использует записи со статусом `verified`. Флаг демокомнаты показывает предупреждение. Выдача черновиков в демокомнате остаётся задачей развития.
- FR-20. Интерфейс эксперта: смотрит клип на аватаре, утверждает или отклоняет с комментарием. Сравнение с оригинальным видео остаётся задачей развития.
- FR-21. Очередь нераспознанных слов: сколько раз встретилось, кнопка «записать жест».
- FR-22. Импорт каталога Slovo из JSON-манифеста и файлов клипов, импорт анимаций VRMA. Экспорт полного словаря остаётся задачей развития.

### 3.6. PWA и мобильный клиент

- FR-23. PWA: manifest, иконки, service worker. Установка на домашний экран Android (Chrome) и iOS (Safari, «На экран Домой»). Сайт полностью работает и во вкладке без установки.
- FR-24. Service worker кэширует статику и клипы жестов: при повторном заходе клипы не скачиваются заново. Новая версия словаря сбрасывает устаревшие клипы.
- FR-25. Wake Lock: экран телефона студента не гаснет, пока открыта комната.
- FR-26. Визуальные и тактильные уведомления: подсветка экрана при новой фразе и при ответе преподавателя в чат, вибрация там, где она поддерживается (Android).
- FR-27. Вход по QR открывает комнату в браузере. Установка PWA предлагается после входа и не обязательна.

### 3.7. Ответ студента жестами

- FR-28. В русскоязычной комнате студент переключается между аватаром с субтитрами и ответом жестами. Браузер запрашивает доступ к камере и показывает предпросмотр.
- FR-29. MediaPipe извлекает координаты кистей и тела в браузере. Система сопоставляет отдельные жесты с 1001 эталоном Slovo. Студент делает паузу, убирая руки из кадра между жестами. Распознанные слова собираются в редактируемый черновик.
- FR-30. Студент подтверждает отправку текста в чат или озвучивает черновик на своём устройстве. При возврате к аватару камера выключается. Камере нужен localhost или HTTPS.

## 5. Архитектура

```
 Браузер преподавателя                 Браузер студента
  микрофон + VAD, текст, чат            VRM-аватар, субтитры, чат
        │ HTTP (фраза) + WebSocket              ▲ WebSocket
        ▼                                       │
 ┌──────────── Caddy / Nginx (HTTPS, статика, клипы) ────────────┐
 └──────────────────────────────┬─────────────────────────────────┘
                                ▼
 ┌────────────── Django (ASGI, uvicorn) ─────────────────────────┐
 │ Auth · Комнаты · Channels (WebSocket) · Админка · HTMX        │
 │ services: asr (Whisper) · gloss (LLM) · compress · пул потоков│
 └──────────────┬──────────────────────────────┬─────────────────┘
                │ SQL                          │ группы Channels
                ▼                              ▼
        ┌──────────────┐               ┌──────────────┐
        │ PostgreSQL   │               │ Redis        │
        └──────────────┘               └──────────────┘
        ┌──────────────┐
        │ Файлы клипов │ (volume, раздаются веб-сервером)
        └──────────────┘
```

**Принципы.**

- Django единственное приложение и владелец схемы БД (миграции Django). Один проект, один деплой.
- Распознавание и LLM живут в том же проекте как модули `services.asr` и `services.gloss` за интерфейсами (Protocol). Позже их можно вынести в отдельный воркер без изменения остального кода.
- Тяжёлые вызовы никогда не выполняются в цикле событий: `asyncio.to_thread` или пул потоков с ограничением числа параллельных задач (семафор). Обращения к ORM из async-кода только через `database_sync_to_async` или async-методы.
- Клиент студента получает готовые глоссы и ссылки на клипы. В режиме ответа жестами браузер сам запускает MediaPipe и распознаёт отдельные жесты.
- Клипы и статика раздаются веб-сервером (Caddy или Nginx) с кэш-заголовками, не через Django.

**Клиент.** Страницы, панели и админка рендерятся шаблонами Django с HTMX. Аватар, запись жестов, микрофон с VAD и PWA это отдельные JS-модули (Vite), которые подключаются на нужных страницах. Аватар работает целиком в браузере (30 FPS, воспроизведение landmarks) и не зависит от перерисовок HTML: страница комнаты не перезагружается, обновления приходят по WebSocket.

### 5.1. Поток данных (одна фраза)

1. Браузер преподавателя: VAD (`vad-web`) определяет конец фразы по паузе и отдаёт аудио фразы целиком (16 кГц, mono, WAV или Opus, 2-8 с). Браузер отправляет её запросом `POST /api/rooms/<code>/phrase/` (multipart).
2. Django принимает файл, отвечает 202 и ставит обработку в фоновую задачу с ограничением параллелизма. Аудио хранится только в памяти и удаляется после распознавания.
3. Фоновая задача: `services.asr.transcribe` (faster-whisper в пуле потоков) возвращает текст. Текст сразу уходит в группу комнаты событием `asr_text` как субтитры, не дожидаясь глосс.
4. `services.gloss.to_glosses`: LLM получает текст, список проверенных глосс из словаря и правила языка, возвращает JSON с глоссами (запасной режим без LLM, если API недоступно).
5. Django сохраняет `Utterance` (текст, глоссы, метрики) и рассылает событие `utterance` всей группе комнаты.
6. Клиент студента ставит глоссы в очередь, подгружает клипы, проигрывает с блендингом и подсвечивает слова в субтитрах. Клиент отправляет `display_started` при выводе субтитров перед загрузкой клипов. Сервер использует событие для индикатора `lag_status`. Задержку до первого жеста следует измерять отдельно.

### 5.2. Распознавание речи: честно про железо

Whisper на CPU слабого сервера будет тормозить, скорость зависит от того, что выделит университет. Варианты по возрастанию стоимости:

1. `faster-whisper` модели `small` (int8) на 4 vCPU: около 1-2 с на фразу 5 с. Достаточно для демо.
2. Запуск проекта на ноутбуке с GPU во время демонстраций (туннель к нему вместо сервера).
3. Внешний API распознавания речи (платный, копейки на объёмах MVP) как запасной режим.
4. Распознавание в браузере преподавателя (transformers.js + WebGPU): сервер для ASR не нужен, готовый текст отправляется на сервер запросом `POST /api/rooms/<code>/text/`. Модель 100-250 МБ грузится один раз и кэшируется. Нужны Chrome или Edge и ноутбук с WebGPU, в Safari хуже. Включается только после проверки качества на русском.

### 5.3. Текст в глоссы

- LLM по API (подойдёт любой с бесплатным тарифом) либо локальная модель через Ollama.
- Промпт: правила порядка слов, пропуск служебных слов, маркеры, few-shot примеры (30-50 пар «фраза → глоссы», подготовленных вместе с экспертом).
- Вывод ограничен JSON-схемой, глоссы выбираются только из словаря проверенных жестов, всё остальное помечается как `fingerspell`.
- Кэш по хэшу фразы (повторы фраз вроде «откройте учебник» бесплатны).
- Правило предохранитель: если LLM недоступна, показываются субтитры и пословные жесты по лемматизации (pymorphy3 для русского), с пометкой «упрощённый режим».

### 5.4. Аватар и клипы

- Рендер: Three.js + `@pixiv/three-vrm`. Модель: VRM из VRoid Studio (бесплатно), лицензия модели проверяется.
- Запись жеста: MediaPipe Holistic (JS) на клиенте редактора, камера обычная.
- Хранение клипа: сырые landmarks (поза, левая и правая рука, лицо) по кадрам, 30 FPS, Float16, gzip. Ретаргет на скелет VRM в браузере через Kalidokit. Преимущество: можно сменить аватара или улучшить ретаргет без перезаписи словаря.
- Сглаживание: One Euro Filter по landmarks на записи и воспроизведении (убирает дрожь пальцев).
- Блендинг: crossfade 150-250 мс между последним и первым кадрами соседних клипов, нейтральная поза в начале и конце каждого клипа.
- Дактиль: отдельные клипы на каждую букву алфавита, склейка с укороченным блендингом.

### 5.5. Сервер университета

Проект размещается на сервере университета, VPS не нужен. Что запросить в неделе 1:

- Виртуальная машина Linux (Ubuntu LTS) с правами sudo, Docker и Docker Compose. Ориентир для прототипа: 4 vCPU, 8-16 ГБ RAM, 50-100 ГБ диска (база и клипы). Если есть GPU, распознавание речи станет заметно быстрее.
- Публичный доступ снаружи: поддомен университета и открытые порты 80 и 443. Студенты заходят с мобильного интернета, а не из сети вуза, и микрофон в браузере работает только по HTTPS.
- Прокси должен пропускать WebSocket (заголовок Upgrade) и не обрывать соединения раньше чем через несколько минут простоя.
- Исходящий доступ с сервера к API языковой модели и к загрузке моделей. Если исходящий трафик закрыт: локальная модель через Ollama и заранее скачанные модели.
- Бэкапы: `pg_dump` по cron и копия на другой хост университета.
- Контакт администратора, который может быстро открыть порт или перезапустить машину.

Если публичный доступ не дадут вовремя, на время демонстраций используется туннель (например, Cloudflare Tunnel) к серверу или ноутбуку.

### 5.6. Структура проекта Django

- `accounts`: пользователь и роли, вход.
- `rooms`: комнаты, участники, чат, consumer, вход по QR и по ID.
- `dictionary`: жесты, клипы, версии словаря, ревью, очередь нераспознанных слов, админка.
- `pipeline`: приём фразы (текстом или аудио), фоновая обработка, `Utterance`, метрики отставания.
- `services`: `asr`, `gloss` (LLM, лемматизация, сжатие), общие интерфейсы провайдеров.
- `frontend`: исходники JS-модулей (аватар, запись жестов, VAD, PWA) и конфиг Vite.
- `config`: настройки, ASGI, маршруты.

**Правила.** Views тонкие, логика лежит в сервисных функциях приложения. Приложения вызывают друг друга только через публичные функции. Один проект, один деплой, одна база.

### 5.7. Порядок и параллелизм обработки фраз

- Фразы одной комнаты обрабатываются строго по порядку: у каждой комнаты одна очередь (`asyncio.Queue`) и одна задача-обработчик. Иначе короткая фраза обгонит длинную, и жесты пойдут не в том порядке.
- Разные комнаты обрабатываются параллельно, но число одновременных распознаваний ограничено глобальным семафором (`ASR_MAX_CONCURRENCY`, по умолчанию число ядер или GPU). Остальные фразы ждут в очереди, преподаватель видит рост отставания.
- Очередь комнаты ограничена (`ROOM_QUEUE_MAX`, ориентир 5 фраз). При переполнении самые старые необработанные фразы пропускаются, преподаватель получает предупреждение «замедлитесь».
- Таймауты: распознавание 20 с, LLM 8 с (ориентиры, задаются в настройках). При превышении фраза показывается только субтитрами, событие `utterance` содержит флаг `degraded`.
- Каждая фраза получает порядковый номер `seq` в пределах комнаты. Клиент студента проигрывает по `seq` и игнорирует повторы после переподключения.
- Очереди хранятся в памяти процесса, поэтому на MVP запускается один процесс uvicorn (`--workers 1`). Для нескольких процессов очереди переносятся в Redis или отдельный воркер.

## 7. Контракты

### 7.1. Сервисные модули ИИ (внутри проекта)

| Модуль | Назначение |
| --- | --- |
| `services.asr.transcribe(audio, lang)` | Вход: байты аудио одной фразы (WAV или Opus 16 кГц mono). Выход: `AsrResult(text, duration_ms)`. По умолчанию faster-whisper в пуле потоков; интерфейс позволяет подменить на внешний API |
| `services.gloss.to_glosses(text, lang, dictionary_version)` | Выход: объект глосс (ниже). По умолчанию LLM, запасной режим: лемматизация `pymorphy3` |
| `services.gloss.compress(text, target_ratio)` | Сжатие длинной фразы при отставании |
| `GET /health/` | Состояние приложения, базы, Redis и загруженных моделей |

Вызовы идут внутри процесса. Тяжёлые (`transcribe`, обращение к LLM) всегда запускаются через `asyncio.to_thread` или пул потоков с семафором, чтобы не блокировать цикл событий и чат комнаты.

### 7.2. Формат глосс

```json
{
  "utterance_id": "u_01H...",
  "lang": "rsl",
  "text": "Откройте учебник на странице десять",
  "sentence_type": "imperative",
  "tokens": [
    {"type": "sign", "gloss": "ОТКРЫТЬ", "src": "Откройте", "markers": []},
    {"type": "sign", "gloss": "УЧЕБНИК", "src": "учебник", "markers": []},
    {"type": "sign", "gloss": "СТРАНИЦА", "src": "странице", "markers": []},
    {"type": "number", "value": 10, "src": "десять"},
    {"type": "fingerspell", "letters": ["И","В","А","Н","О","В"], "src": "Иванов"}
  ],
  "unknown": ["Иванов"]
}
```

Маркеры (`markers`): `neg` (отрицание), `q-yn` и `q-wh` (вопрос), `cond` (условие), `emph` (акцент). Они управляют мимикой и поворотом головы аватара: набор мимических режимов задаётся вместе с экспертом и хранится в конфиге.

### 7.3. События WebSocket (Django Channels)

| Событие | Направление | Содержимое |
| --- | --- | --- |
| `asr_text` | сервер → все | распознанный текст фразы (показывается сразу, до глосс) |
| `utterance` | сервер → все | объект глосс + ссылки на клипы |
| `chat_message` | клиент ↔ все | `{user, body, ts}` (клиент отправляет `{type: chat, body}`) |
| `display_started` | студент → сервер | `{utterance_id, ts}` для расчёта отставания |
| `lag_status` | сервер → препод | `{lag_ms, level}` |
| `unknown_words` | сервер → препод | список слов без жеста |
| `presence` | сервер → все | список участников, вход и выход |
| `room_closed` | сервер → все | комната закрыта преподавателем |

**Изоляция комнат.** Каждая комната это отдельная группа Channels `room_<id>`. В `connect()` consumer проверяет на сервере, что комната открыта и код верный (для студента ещё и гостевую сессию с именем), и только потом добавляет соединение в группу. HTTP-запросы к API проверяются так же: участник видит данные только своей комнаты. Скрытие данных в интерфейсе изоляцией не считается.

### 7.4. HTTP API (Django)

- `GET /api/dictionary/?lang=rsl&status=verified` , список глосс и версия словаря.
- `GET /media/clips/<id>.json.gz` , файл клипа, раздаёт веб-сервер с кэш-заголовками (ETag).
- `POST /api/signs/` , создание жеста редактором (метаданные и файл клипа).
- `POST /api/signs/<id>/review/` , решение эксперта.
- `POST /api/rooms/<code>/phrase/` , аудио фразы (только преподаватель комнаты), ответ 202.
- `POST /api/rooms/<code>/text/` , фраза текстом (только преподаватель комнаты), ответ 202.
- `GET /health/` , состояние.

**Комнаты и вход.** `POST /api/rooms/` создаёт комнату и возвращает ID. Страница `GET /r/<code>/` открывает комнату (по ней ведёт QR-код). Главная страница принимает ID и перенаправляет на `/r/<code>/`. QR генерируется на сервере (библиотека `segno`, SVG), ссылка в нём всегда `/r/<ID>/`. WebSocket комнаты: `/ws/rooms/<code>/`.

### 7.5. Формат клипа

```json
{
  "version": 1,
  "gloss": "УЧЕБНИК",
  "fps": 30,
  "frames": 54,
  "layout": {"pose": 33, "hand_l": 21, "hand_r": 21, "face": 468},
  "data": "<base64 gzip Float16 [frames x points x 3]>"
}
```

Хранится файлом `.json.gz` (или бинарным `.sc` позже). Лицо можно хранить сокращённо (брови, глаза, рот, около 60 точек) для экономии размера.

### 7.6. Протокол WebSocket: формат, переподключение, presence

- Подключение: `/ws/rooms/<code>/`. Все сообщения JSON с полем `type`. Серверные события комнаты несут `seq` (фразы) или `id` (чат).
- Клиент отправляет: `{type: chat, body}` (до 500 символов), `{type: display_started, utterance_id, ts}`, `{type: ping}`. Сервер отвечает на `ping` сообщением `{type: pong}`.
- Heartbeat: клиент шлёт `ping` раз в 20 с, сервер закрывает соединение без пинга 60 с. Это не даёт прокси оборвать простаивающее соединение и делает presence точным.
- Переподключение: клиент повторяет попытки с нарастающей паузой (1, 2, 4, 8 с, потолок 15 с). После подключения он запрашивает пропущенное: `GET /api/rooms/<code>/history/?after_seq=<n>&after_message_id=<m>` возвращает пропущенные фразы (с глоссами) и сообщения чата. Затем возобновляется приём событий, дубликаты отсекаются по `seq` и `id`.
- Presence: при `connect` участник записывается в Redis (множество комнаты с TTL, продлевается по `ping`), при `disconnect` или истечении TTL удаляется. Изменения рассылаются событием `presence`. У участника может быть несколько соединений (вкладки): он онлайн, пока есть хотя бы одно.
- Закрытие комнаты: сервер рассылает `room_closed` и закрывает соединения. Коды закрытия: 4401 нет сессии, 4403 нет доступа или комната закрыта, 4429 превышен лимит. На 4401 и 4403 клиент не переподключается.

## 8. Схема базы данных (Django ORM)

| Модель | Поля |
| --- | --- |
| `User` | id, email, name, role (teacher/editor/expert/admin), password, created\_at |
| `Room` | id, title, owner (FK User), lang, status (open/closed), join\_code (6 символов, уникальный среди открытых комнат), demo\_mode (bool), created\_at, closed\_at |
| `Participant` | room, user (nullable) или guest\_name, session\_key, joined\_at, removed\_at |
| `Message` | id, room, participant, body, created\_at |
| `Utterance` | id, room, text, glosses (JSONField), asr\_ms, gloss\_ms, display\_lag\_ms, started\_at |
| `Sign` | id, gloss, lang, description, status (draft/review/verified/rejected), recorded\_by, verified\_by, verified\_at, comment |
| `SignClip` | id, sign (FK), file (FileField), fps, duration\_ms, frames, version, size\_bytes |
| `UnknownWord` | id, lemma, lang, count, last\_seen\_at, status (new/queued/recorded) |
| `DictionaryVersion` | id, lang, number, created\_at (версия растёт при утверждении жеста) |

Ограничения и индексы: `Sign(gloss, lang)` уникальный для проверенных (UniqueConstraint с условием), `Message(room, created_at)`, `UnknownWord(lang, -count)`. Опционально позже: расширение `pgvector` для поиска ближайшего жеста по смыслу.

## 9. Процесс создания словаря

1. Эксперт (или носитель) определяет список жестов темы MVP: 100-300 слов + алфавит + цифры.
2. Редактор записывает каждый жест в инструменте: 2-3 дубля, выбирается лучший.
3. Эксперт проверяет: смысл, скорость, положение, мимика. Статус «проверен» ставит только он.
4. Нераспознанные слова из реальных занятий попадают в очередь записи, словарь растёт.
5. Версия словаря фиксируется, глоссы в LLM-промпте берутся только из текущей версии.

**Источники ускорения.** Открытые датасеты РЖЯ (например, Slovo) можно использовать как справочник и для автоматического черновика клипов. Проверьте лицензии. Комплект для демонстрации содержит 1003 клипа Slovo. При запуске с пустым словарём Compose импортирует клипы со статусом `verified`. Для приёмки учебного пилота количество подтверждённых экспертом жестов учитывается отдельно.

## 10. Исходный план реализации (12 недель, команда 2-3 человека)

| Этап | Недели | Результат |
| --- | --- | --- |
| 0. Подготовка | 1 | Язык MVP зафиксирован: русский (русская речь и РЖЯ); выбрана тема MVP; запрошены ресурсы университета (VM, домен, порты 80 и 443, GPU если есть), найден эксперт-носитель (общество глухих, педвуз), репозиторий, docker-compose, CI |
| 1. Каркас | 2-3 | Django: авторизация, комнаты с QR-кодом и входом по ID, чат, presence, панель преподавателя (шаблоны и HTMX), ввод текстом |
| 2. Аватар | 3-5 | VRM на странице студента, проигрывание клипа из landmarks, блендинг, 20 тестовых жестов, дактиль, PWA (manifest, service worker, кэш клипов), проверка на iPhone и Android |
| 3. Словарь | 4-6 | Инструмент записи жестов в браузере, статусы, интерфейс эксперта, админка |
| 4. Глоссы | 6-8 | Сервисный модуль `services.gloss`, промпты, кэш, интеграция, очередь клипов и субтитры |
| 5. Голос | 8-10 | Микрофон, VAD, Whisper, индикатор отставания, сжатие фраз, очередь нераспознанных |
| 6. Наполнение и тесты | 10-11 | 100-300 проверенных жестов, тестовые занятия с 3-5 глухими или слабослышащими студентами, правки по отзывам |
| 7. Выпуск | 12 | Деплой, бэкапы, демо-видео, документация, питч |

Этапы 2-3 и словарь идут параллельно: пока один пишет код, второй записывает жесты с экспертом. Наполнение словаря начинается с недели 4 и не заканчивается.

**Критерий перехода:** каждый этап заканчивается рабочим демо. Если на конец недели 6 цепочка «текст → глоссы → клипы → чат» не работает, остальное откладывается.

## 11. Критерии приёмки MVP

| Критерий | Результат сверки |
| --- | --- |
| Конец фразы → первый жест. Медиана ≤ 4 с, p95 ≤ 7 с | Требуется замер фактического начала жеста. |
| ≥ 100 жестов с экспертным подтверждением, полный дактиль и числа 0–100 | Требуется проверка состава и экспертная приёмка. |
| ≥ 80% покрытия на 30 типовых фразах темы | Требуется тематический набор и прогон. |
| Понятность ≥ 3,5 из 5 при субтитрах, минимум три глухих или слабослышащих участника | Требуется пользовательское тестирование. |
| 30 студентов одновременно | Подключения, presence и чат проверены. Воспроизведение аватара под нагрузкой требует прогона. |
| Развёртывание одной командой за ≤ 15 минут | Запуск из чистой копии подтверждён. Время установки требует отдельного замера. |
| PWA, микрофон и кэш клипов на Android и iPhone | Требуется проверка на устройствах. Целевые 30 FPS и матрица браузеров также требуют проверки. |

Известное ограничение плеера: фраза со смесью VRMA и клипов из ключевых точек может проигрываться частично.

## 12. Риски

| Риск | Вероятность | Что делаем |
| --- | --- | --- |
| Нет эксперта-носителя | Средняя | Привлечь носителя РЖЯ для проверки стартовых клипов и понятности аватара перед учебным пилотом |
| Непроверенные жесты видят студенты | Высокая на старте | Демо-режим комнаты с заметной пометкой «прототип, жест не проверен носителем»; на реальных занятиях только проверенные жесты |
| Аватар «дрожит», пальцы нечитаемы | Высокая | Сглаживание, запись при хорошем свете, ограничение жестами, где руки хорошо видны, ручная правка |
| Сервер университета не тянет Whisper | Средняя | Модель `small` int8, запросить сервер с GPU, GPU-ноутбук на демо, внешний API как запасной |
| Сеть университета закрывает вход снаружи или исходящие запросы | Средняя | Запросить домен и порты 80 и 443 в неделе 1, туннель на время демо, локальная модель вместо внешнего API |
| Рост отставания | Высокая | Индикатор для препода, сжатие фраз, ускорение клипов |
| Скепсис сообщества глухих | Средняя | Привлекать глухих консультантов к дизайну, позиционировать как ассистента, собирать обратную связь открыто |
| LLM ошибается в грамматике жестового языка | Высокая | Few-shot от эксперта, ограничение словарём, тестовый набор, проверка эксперта на типовых фразах |
| Закончится бесплатный тариф LLM | Средняя | Кэш фраз, локальная модель, упрощённый режим |
| Правовые вопросы (данные студентов) | Низкая | Не хранить аудио, согласие, минимум персональных данных |

**Дополнительный риск: iOS и PWA.** Доступ к микрофону и поведение service worker в установленном PWA на iPhone отличаются от Android. Проверять на реальном устройстве уже на этапе 2, не в конце проекта.

## 13. Ресурсы при бюджете ноль

- Хостинг: сервер университета (виртуальная машина или выделенный сервер); запасной вариант VPS около 5 долларов в месяц.
- База: Postgres в Docker на том же сервере, бэкапы на другой носитель университета.
- Модели: Whisper и VAD локально, LLM по бесплатному тарифу или Ollama.
- Люди: эксперт-консультант (волонтёр, педагогический вуз, общество глухих) за соавторство или пилот. Остальное делает команда.
- Финансирование позже: хакатоны социальных проектов, гранты для студенческих стартапов, научный проект или диплом в вузе.

## 14. Открытые вопросы

1. **Язык первой версии:** решено: русский (русская речь и РЖЯ), казахский позже. Подтвердить с экспертом, что РЖЯ подходит аудитории пилота.
2. **Какая предметная область MVP:** школьное обращение преподавателя, один предмет, колледж?
3. **Кто эксперт:** контакт с обществом глухих или педвузом, нужен до конца недели 1.
4. **Вход студента без регистрации (по имени):** принято в ТЗ по умолчанию, подтвердить с преподавателем.
5. **Модель аватара:** собственная VRM или готовая, проверить лицензию.
6. **Ресурсы сервера:** есть ли GPU, сколько ядер и памяти выделит университет. Это определяет скорость распознавания и число одновременных лекций.
7. **Провайдер LLM:** какой API или локальная модель, и доступен ли внешний API из сети университета.
8. **Одновременные лекции:** сколько их ожидается. Нагрузка считается по лекциям, а не по числу студентов.

## 15. Исходный план генерации проекта через ИИ-агента (OpenCode)

Раздел 10 описывает работу команды по неделям. Этот раздел описывает, как собрать код ИИ-агентом маленькими проверяемыми этапами. Дешёвая модель надёжнее справляется с небольшой задачей, у которой есть команда проверки, чем с запросом «сгенерируй проект». Этапы со звёздочкой ★ сложные (интеграции, ретаргет, конкурентность): их лучше прогонять более сильной моделью, остальные подходят дешёвой.

### 15.1. Правила для агента

1. Один этап = одна новая сессия с чистым контекстом и отдельная git-ветка. Агент получает только нужные куски ТЗ (контракт, схему, FR этапа), а не весь документ.
2. В начале сессии агент читает `AGENTS.md` и `docs/STATE.md`. В конце обновляет `docs/STATE.md`: что готово, какие модули и публичные функции появились, что дальше.
3. `AGENTS.md` создаётся на этапе A1 и содержит: версии Python, Django, Channels и Node (зафиксированы, агент их не обновляет); структуру приложений из раздела 5.6; соглашения (тонкие views, логика в сервисных функциях, где лежит клиентский код); запреты (не добавлять зависимости без запроса, не менять чужие приложения, не переписывать готовые тесты).
4. Перед использованием API любой библиотеки агент читает её документацию и исходники в `site-packages` и `node_modules`, а не пишет по памяти. Особенно это важно для Channels, `django-vite`, three-vrm и Kalidokit.
5. Тесты пишутся вместе с кодом. Этап закрыт только когда проходит `make check` (`ruff check`, `pytest`, для клиента `npm test`).
6. Коммит после каждого этапа. Если агент зациклился или сломал соседнее приложение, ветка выбрасывается и этап запускается заново с уточнённым промптом, а не чинится в той же сессии.
7. Мелкие этапы лучше крупных: если этап не укладывается в одну сессию, его делят пополам.
8. В async-коде (consumer, async view) блокирующие вызовы запрещены: ORM только через `database_sync_to_async` или async-методы, тяжёлые операции (Whisper, LLM) через `asyncio.to_thread`.

Шаблон промпта этапа:

```
Прочитай AGENTS.md и docs/STATE.md. Задача этапа <номер>: <описание>.
Контекст из ТЗ: <вставленные разделы>.
Не меняй приложения вне этой задачи, не добавляй зависимости. Напиши тесты.
Закончи, когда проходит: make check. Обнови docs/STATE.md.
```

## 17. Безопасность и данные

- **Сессии.** Роли определяются сессией Django (cookie `HttpOnly`, `Secure`, `SameSite=Lax`). Студент получает гостевую сессию после ввода имени.
- **CSRF.** POST-запросы из браузера идут с токеном CSRF (заголовок `X-CSRFToken`), включая отправку фраз.
- **WebSocket.** Проверка `Origin` (`AllowedHostsOriginValidator`) и сессии в `connect()`. Сообщения проверяются по роли: писать в чат может любой участник комнаты, отправлять фразы и текст только преподаватель этой комнаты.
- **Ограничение частоты** (значения ориентировочные, в настройках): вход по ID 10 попыток в минуту на IP, чат 5 сообщений за 5 секунд на участника, отправка фраз не чаще одной в секунду.
- **Аудио.** Лимит размера файла (ориентир 2 МБ) и длительности (до 30 с), проверка типа. Файл не пишется на диск и удаляется из памяти после обработки.
- **Персональные данные.** Аудио не хранится. Хранятся имя гостя, текст чата и фраз. Срок хранения задаётся настройкой (ориентир 90 дней), старые записи удаляет команда по cron. Согласие на обработку показывается при входе.
- **Секреты.** Ключ LLM, пароль базы и `SECRET_KEY` только в переменных окружения, `.env` не коммитится.
- **Клипы.** Загружать их может только роль editor, формат клипа валидируется (версия, размеры, число кадров не выше лимита).
- **Продакшен.** `DEBUG=False`, `ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS` с реальным доменом, HTTPS и HSTS.

## 18. Окружение и развёртывание

### 18.1. Комплект Docker Compose

Проект использует Django с uvicorn, PostgreSQL, Redis и Caddy. В репозиторий входят аватар VRM, исходник Blender, анимации VRMA, модель MediaPipe и каталог Slovo. Фактические настройки определяет `docker-compose.yml`.

### 18.2. Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` | Базовые настройки Django |
| `DATABASE_URL`, `REDIS_URL` | Подключения к Postgres и Redis |
| `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY` | Провайдер LLM (API или локальная Ollama) |
| `WHISPER_MODEL`, `WHISPER_DEVICE` | Модель распознавания (`small`) и устройство (`cpu` или `cuda`) |
| `ASR_MAX_CONCURRENCY`, `ROOM_QUEUE_MAX` | Параллелизм распознавания и размер очереди комнаты |
| `MEDIA_ROOT`, `RETENTION_DAYS` | Каталог клипов и срок хранения чата и фраз |

### 18.3. Развёртывание

1. Скачать или клонировать репозиторий. В каталоге с `docker-compose.yml` выполнить `docker compose up --build` и открыть `http://localhost:8000`.
2. При первом запуске нужен интернет для сборки и загрузки весов Whisper. Скрипт запуска применяет миграции и заполняет пустой словарь. `GET /health/` проверяет доступность базы.
3. Для серверного запуска настроить `.env` по `.env.example`, домен, HTTPS и резервное копирование базы и клипов.
4. Для обновления выполнить `git pull --ff-only` и `docker compose up -d --build`.
